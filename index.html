AWS Cloud Concepts

1.1

Introduction to Cloud Computing

Storing and accessing data and programs on remote servers hosted on the internet, instead of a computer's hard drive or a local server.

Working definition "Cloud Computing is a technology that facilitates users in accessing and utilizing computing resources over the internet, offering scalability and flexibility." Cloud combines compute, database, networking, storage, OS, security, and architecture — provisioned via the internet, on demand.
What server hardware actually provides

Storage

Persistent data — HDD (cheap, slower) and SSD (fast, costlier). Measured by IOPS (reads/writes per second) and throughput (bytes/sec — high for SSD, low for HDD).

Compute

CPU — generic instruction processor, max ~10 cores; the OS relies on it.

Memory

RAM — fast, volatile, holds data actively being processed.

GPU

Thousands of cores for parallel processing of large data volumes — specialized, not general-purpose.

A data center is a collection of this server hardware — typically 50,000–80,000 servers, organized into racks (a rack = a collection of servers).

How AWS answers HDD/SSD needs

Amazon EFS

Serverless, set-and-forget file system for AWS compute — scales storage automatically.

Amazon S3

Object storage — availability, security, performance, industry-leading scalability.

AWS Storage Gateway

Virtually unlimited cloud storage extended to on-premises applications.

Amazon EBS

Low-cost, cold HDD-class block storage in the cloud.

The over-provisioning problem — why cloud exists
Traditional (on-premises) computing Infrastructure as hardware: needs space, staff, physical security, capital expenditure, a long procurement cycle, and provisioning capacity by guessing the theoretical peak — leading to over-provisioning (paying for far more than you use) and long customer waiting during under-provisioning.
Cloud computing Infrastructure as software: flexible, changes quickly and easily, and eliminates the "undifferentiated heavy lifting" of maintaining data centers.
Virtualization

The software technology that creates logical isolation of physical resources (RAM, CPU, storage) so multiple virtual instances can share one physical machine. A hypervisor is the software used to run multiple VMs on a single physical machine.

Partitioning

Run multiple servers simultaneously on one physical server.

Encapsulation

An entire virtual server (including boot disks) is packaged as a file.

Isolation

Virtual servers on the same physical host are safely separated — one can't affect another's tasks.

Hardware Independence

A running virtual server can migrate across different hardware platforms.

Characteristics of cloud computing

Scalability

Flexible server size/number — adjusts to demand surges.

Save Money

No in-house hardware purchase — vendor owns the equipment.

Reliability

A network of servers keeps resources available even if one server goes offline.

Physical Security

Underlying servers sit in data centers with strong on-site security.

Outsourced Management

Someone else manages the infrastructure — you don't worry about degradation.

Architecture of cloud computing

1 · Front End

Thin clients — lightweight, browser-based, portable. Fat clients — more local functionality for a stronger user experience.

2 · Back-End Platforms

The cloud computing engine — servers for storage and processing, application-logic management, and effective data handling.

3 · Cloud-Based Delivery & Network

Internet (global access), Intranet (internal comms), Intercloud (interoperability across cloud services).

Advantages

Cost Efficiency

Pay-as-you-go — lowers capital expenditure, especially for SMBs.

Flexibility & Scalability

Scale resources to demand without large hardware investment during low-demand periods.

Collaboration & Accessibility

Access data/apps from anywhere — real-time shared documents and projects.

Automatic Maintenance

AWS handles infrastructure management and keeps software current automatically.

Disadvantages

Security Concerns

Sensitive data on external servers raises exposure risk.

Downtime & Reliability

Server, network, or maintenance issues can cause unexpected interruptions.

Internet Dependency

Requires stable, high-speed connectivity — a real constraint in low-connectivity regions.

Cost Management Complexity

Pay-as-you-go can lead to unexpected costs without careful monitoring.

Cloud sustainability & security

Sustainability levers

Energy-efficient data center operation, adoption of renewable energy (solar/wind), and virtualization to cut the number of physical servers needed.

Security best practices

Data Encryption (unreadable if intercepted), Access Control (strict authentication), MFA (multiple verification factors before access).

Use cases

Scalable infrastructure (IaaS), efficient application development (PaaS), streamlined software access (SaaS), big data analytics, and cost-effective disaster recovery.

1.3

Cloud Service Models

IaaS, PaaS, and SaaS differ in exactly one thing: how much of the stack you manage versus how much the vendor manages.

IaaS — Infrastructure as a Service

Virtualized VMs, storage, networks. You control the OS and applications. Flexibility: full control. Cost: eliminates physical infrastructure investment. Scalability: hardware scales up/down on demand.

PaaS — Platform as a Service

Infrastructure is abstracted away; you focus purely on application logic/code. Speeds up execution and time-to-market. Resource scaling is automated for you.

SaaS — Software as a Service

Fully managed software delivered over the internet — no local install. Automatic updates/patches. Cost-effective — no individual software licenses.

1.4

Cloud Deployment Models

Defines where your servers live and who controls them — based on ownership, scale, and access.

Public Cloud

Infrastructure is owned by the provider, not the consumer — services are delivered over the internet to the general public or industry groups. Example: Google App Engine. AWS's public-cloud service is Amazon EC2, hosted in an identified AWS Region — the customer has no control over exactly where it's hosted but can use it anytime, anywhere.

Advantages

  • Minimal investment — pay-per-use, no big upfront fee
  • No setup cost — provider subsidizes the infrastructure
  • No infrastructure management needed
  • Dynamic scalability on demand

Disadvantages

  • Less secure — shared, publicly accessible resources
  • Low customization — shared by many tenants
  • No maintenance control — handled by the provider

Well suited for: data storage/archival, application hosting, latency-tolerant or non-mission-critical web tiers, on-demand microsite hosting, and auto-scaling environments for large applications.

Private Cloud

The exact opposite of public — a one-on-one environment for a single customer, no shared hardware. Also called the "internal cloud." Implemented in a secure environment behind firewalls, under an organization's IT department. AWS's private-cloud service is Amazon VPC.

Advantages

  • Better control — full ownership of integration, IT ops, policy
  • Data security & privacy — access restricted to authorized staff
  • Supports legacy systems that can't use the public cloud
  • Customization to specific needs

Disadvantages

  • Less scalable — smaller client base to spread cost
  • Costlier — personalized facilities cost more

Chosen for: strict security/latency/regulatory/privacy requirements, highly regulated organizations, orgs large enough to absorb the cost, high-performance file-system access (e.g. media companies), and business-critical data/applications.

Hybrid Cloud

Bridges public and private with a layer of proprietary software — host in a secure private environment while still using the public cloud's cost savings. Uses at least one private and one public cloud (can use multiple of each).

Advantages

  • Flexibility & control — personalized solutions
  • Cost — only pay for extra public-cloud capacity when needed
  • Security — data properly separated, reducing theft risk

Disadvantages

  • Difficult to manage — combines two different environments
  • Slower data transmission — public-cloud leg adds latency

Best for: large organizations wanting public-cloud flexibility, vertical-market services (customer interactions public, company data private), and organizations needing mission-critical data private while dev/test happens on the public cloud.

1.5

AWS Global Infrastructure

Built around two nested concepts: Regions, and the Availability Zones inside them.

Region

A physical location in the world containing multiple Availability Zones. Three or more AZs make up a Region.

Availability Zone (AZ)

One or more discrete data centers with redundant power, networking, and connectivity, in separate facilities — a cluster of data centers, physically separated by 10–100 km with high isolation, designed for fault isolation.

Current scale AWS spans 33 launched Regions and 105 Availability Zones, with 600+ CloudFront POPs and 13 Regional edge caches — plus announced plans for 18 more AZs and 6 more Regions (Malaysia, Mexico, New Zealand, Saudi Arabia, Thailand, and the AWS European Sovereign Cloud). In India: ap-south-1 (Mumbai) and ap-south-2 (Hyderabad).
Choosing a Region — 4 factors

Data Governance

Legal requirements, e.g. GDPR compliance.

Proximity

Latency to your customers.

Service Availability

Not every service is in every Region.

Cost

Pricing varies by Region.

The three pillars of AWS's global footprint

Security

Custom-built for cloud use, monitored 24/7 for confidentiality, integrity, and availability. All global network traffic is encrypted; users control their own data.

Availability

Highest network availability among cloud providers — each Region is fully isolated with multiple AZs; apps can be partitioned across AZs in the same Region.

Flexibility

Choose how and where to run workloads — same network, control plane, APIs, and services everywhere.

High performance is delivered through Regions, AWS Local Zones, and AWS Wavelength, riding a redundant 400 GbE fiber backbone for low latency and packet loss.

1.6

AWS Shared Responsibility Model

Security is a two-party job — and exactly where the line falls depends on which service you're using.

AWS: "Security OF the Cloud"

AWS is responsible for protecting the infrastructure that runs every AWS Cloud service — the hardware, software, networking, and facilities.

Customer: "Security IN the Cloud"

Determined by which services you choose. For EC2 (IaaS), you manage the guest OS, application software, and firewall configuration on each instance.

Encryption note Symmetric encryption is used for data at rest. Asymmetric encryption (private + public key pair) is used for data in transit.
Abstracted services shift more to AWS For services like Amazon S3 and DynamoDB, AWS manages the infrastructure, OS, and platform — while customers manage their data, classify assets, and apply permissions via IAM. This relieves customers of operating controls tied to physical infrastructure.
Three control types

Inherited Controls

Fully inherited from AWS — e.g. physical and environmental controls.

Shared Controls

Apply to both infrastructure and customer layers, in separate contexts. AWS provides the infrastructure requirement; the customer implements their own control on top of it.

Customer-Specific Controls

Solely the customer's responsibility, based on the application they're deploying.

2.2

Amazon S3 (Simple Storage Service)

Object storage with industry-leading scalability, availability, security, and performance.

Why S3 is preferred Claims 99.999999999% (11 nines) durability — store 10,000,000 objects and expect to lose one only every 10,000 years. S3 automatically creates and stores copies of every object across many systems.
Core concepts

Regions

Chosen to optimize latency, cost, or regulatory need. Objects never leave the Region unless explicitly transferred.

Data Consistency Model

Read-after-write consistency for new object PUTs (immediately readable). Eventual consistency for overwrite PUTs and DELETEs.

Key

Unique identifier for an object. An object = bucket name + key (+ optional version ID).

Buckets

Containers for objects — unlimited objects per bucket, no nesting, non-transferable ownership, only the owner can delete.

Objects

Data + metadata (default like last-modified/content-type, plus custom metadata). Files range from 0 Bytes to 5 TB.

S3 is a universal namespace — bucket names must be globally unique, since a bucket maps to a DNS address.

Core features

Durability & Availability

Redundant storage across multiple facilities within a Region.

Scalability

Elastically supports virtually unlimited storage.

Lifecycle Management

Auto-migrate objects to cheaper classes or delete as they age.

Access & Security

Bucket policies, ACLs, IAM integration for fine-grained control.

Encryption

SSE with S3-managed keys, KMS keys, or customer-provided keys.

Versioning

Keep multiple variants of an object — recover from unintended actions.

Access Logs

Log all bucket requests for auditing/compliance.

Cross-Region Replication

Auto-replicate objects to other Regions for DR or low-latency access.

Use cases

Data lakes (centralized repository for structured/unstructured data at any scale — dashboards, big data processing, real-time analytics, ML), backup & restore, static website hosting (paired with CloudFront), and big data analytics (integrates with Athena, Redshift, EMR).

Features by category

2.4

Amazon VPC (Virtual Private Cloud)

A logically isolated virtual network you fully define — resembling a traditional data-center network, but built on AWS's scalable infrastructure.

Fundamentals

Public Subnet

Has internet access (route to an Internet Gateway).

Private Subnet

No internet access. If it needs outbound access, it must go through a NAT in a public subnet.

A subnet must reside entirely within one Availability Zone. VPC Security Groups manage both inbound and outbound traffic (plain EC2 security groups only define inbound rules). The Route Table specifies subnet IP routing.

Architecture, traced end to end Region → VPC → (Internet Gateway / Virtual Private Gateway connect from outside) → Router → Route Table → Network ACL (stateless firewall, allow/deny by IP) → Security Group (stateful, per-instance) → Public / Private Subnets. To reach a private-subnet instance, you SSH into the public subnet first, then jump across — a jump box.
Key concepts

CIDR Block

The IPv4 range you assign the VPC, e.g. 10.0.0.0/16 — sets the size of its private address space.

Subnets

Segments of the VPC's address range, each tied to one AZ.

Internet Gateway

Horizontally scaled, redundant component enabling VPC ↔ internet communication.

Route Tables

Rules ("routes") determining where traffic is directed; every subnet needs one.

Security Groups vs NACLs

Security Groups = stateful, instance-level firewall. NACLs = stateless, subnet-level, optional extra layer.

VPC Peering

Connects two VPCs via a direct private-IP route — traffic flows as if on one network.

VPN Connections

Encrypted link between your on-premises network and your VPCs.

VPC Endpoints

Private connection to supported AWS services via PrivateLink — no internet gateway/VPN/Direct Connect needed.

Elastic IP

A static public IPv4 address reserved to your account until you release it.

Benefits & use cases

Benefits

  • Isolation, IP-range control, security-group/NACL layering
  • Static IPv4 persists across instance start/stop
  • Scales horizontally across multiple AZs
  • Integrates with EC2, RDS, Lambda, and more

Use cases

  • Hosting public-facing websites/apps
  • Limiting web/app/DB server connectivity via peering
  • Migrating workloads to AWS

Amazon Redshift

A fully managed, petabyte-scale data warehouse for fast, cost-effective OLAP analytics — launched by AWS in 2013.

What makes it fast Redshift is an OLAP, column-oriented database based on PostgreSQL 8.0.2 — regular SQL works, but the real differentiator is Massively Parallel Processing (MPP) (technology from ParAccel): many processors, sometimes across multiple servers, work in parallel on the same query.
Cluster architecture

Leader Node

Manages all client/compute-node communication. Parses queries, builds execution plans, compiles code, and distributes it — plus assigns a data portion to each compute node. Queries not touching compute-node tables run entirely on the leader node.

Compute Nodes

Run the compiled code and return intermediate results to the leader node for final aggregation. Each has dedicated CPU/memory; add nodes or upgrade node type to grow capacity. Each node is partitioned into slices that process work in parallel.

Redshift Managed Storage (RMS)

A separate storage tier that scales to petabytes on Amazon S3 — lets you size compute independently of storage. Uses high-performance SSD as tier-1 cache, with automatic optimization by data block temperature/age/workload pattern.

Client Applications

Interact only with the leader node. Since Redshift is PostgreSQL-based, most existing SQL/BI/ETL tools work with minimal changes.

Data distribution styles

KEY

Distributes by a column value — rows with the same value land together, optimizing joins.

EVEN

Spreads rows evenly across all slices — good for uniform distribution.

ALL

Copies data to every node — ideal for small, frequently-joined tables.

Security features

Encryption: data at rest via AWS KMS or customer-managed keys; in transit via SSL. Network isolation: deploy inside a VPC; PrivateLink for private AWS-service communication without the public internet. Access control: IAM integration for fine-grained, least-privilege permissions, plus database-level user/role management. Audit logging: database audit logs record connections, queries, and object changes — sendable to CloudTrail for long-term storage and analysis.

Benefits

Speed (MPP)

Unmatched output speed on large datasets at the price point.

Data Encryption

You choose which operations to encrypt — an added security layer.

Familiar Tools

PostgreSQL-based — any SQL/ETL/BI tool works, no lock-in to AWS-only tooling.

Intelligent Optimization

Suggests query and automatic-maintenance improvements for faster, less resource-intensive runs.

Automate Repetitive Tasks

Scheduled reports, cost/resource audits, and maintenance clean-ups.

Scales automatically to absorb increasing concurrent workloads.

AWS Disaster Recovery & Backup

Preparing for and recovering from a disaster — an event that stops a workload fulfilling its business objectives at its primary location.

What counts as a disaster

Natural

Earthquakes, floods, and similar events.

Technical

Power failure, network connectivity loss.

Human

Inadvertent misconfiguration, or unauthorized/outside access or modification.

Disaster recovery vs. availability Both are part of a resiliency strategy, but DR measures objectives for a one-time event, while availability objectives measure mean values over a period of time. AWS Elastic Disaster Recovery (AWS DRS) minimizes downtime/data loss for on-premises and cloud-based apps using affordable storage, minimal compute, and point-in-time recovery.
Recovery objectives

RTO — Recovery Time Objective

The maximum acceptable delay between a service interruption and its restoration — the acceptable downtime window, set by the organization.

RPO — Recovery Point Objective

The maximum acceptable time since the last data-recovery point — the acceptable amount of data loss between the last recovery point and the interruption.

DR strategies (low → high cost/complexity)
1

Backup and Restore

Suitable for mitigating data loss/corruption; can mitigate a regional disaster by replicating data to other Regions. Beyond data, you must also redeploy infrastructure, configuration, and application code in the recovery Region.

2

Pilot Light

Replicate data to another Region and keep a copy of core infrastructure. Data-related resources (databases, object storage) stay always-on; other elements (e.g. app servers) are pre-configured but "switched off" until failover or testing. Minimizes ongoing cost while keeping recovery fast, since core infra is already in place.

3

Warm Standby

Named in the syllabus as a more advanced active/passive strategy beyond Pilot Light, for disasters at Region scale or under regulatory requirements — a scaled-down but fully functional copy of the production environment is always running.

4

Multi-Site Active/Active

The most complex, highest-availability strategy — multiple active Regions serve traffic simultaneously rather than one active and one passive site.

Active/passive strategies use an active site (e.g. one AWS Region) to serve traffic while a passive site (a different Region) stands by for recovery and doesn't serve traffic until failover triggers. For maximum resiliency, prefer data plane operations (real-time service delivery) over control plane operations (environment configuration) in your failover path — data planes typically have higher availability design goals.

Shared Responsibility Model for Resiliency AWS — "Resiliency of the Cloud": the hardware, software, networking, and facilities running AWS Cloud services. Customer — "Resiliency in the Cloud": depends on the services you choose. E.g. EC2 requires you to handle all resiliency configuration (multi-AZ deployment, Auto Scaling, resilient architecture); for managed services like S3 and DynamoDB, AWS runs the infrastructure/OS/platform and you just use the endpoints.

AWS Identity and Access Management (IAM)

A web service for securely controlling who can access which AWS resources, and what they can do with them.

Root user The account used to sign in (email + password at account creation) is the root user — unrestricted rights, access to every part of the account. Best practice: create an admin user with fewer powers rather than using root day-to-day.
How IAM works — 6 steps
1

The entity taking action — a user, role, or application.

2

Confirming the principal's identity via credentials/keys.

3

Request

The principal specifies the action and target resource.

4

Denied by default — allowed only if a matching policy permits every part of the request.

5

View, create, edit, or delete a resource.

6

The set of AWS assets the actions apply to.

Core components

Users

Individual people or services granted access.

Groups

Collections of users managed as one — members inherit the group's permissions.

Roles

Delegate access without sharing long-term credentials — ideal for temporary or service-to-service access.

Policies

JSON documents specifying allowed/denied actions, attached to users, groups, or roles.

Access key ID + secret key, used by programmatic users (apps, CLI) instead of a console login.

Federation

IAM Identities & Policies

IAM Users — access the console with permissions distinct from root (e.g. a user with read-only EC2 access). IAM Groups — manage permissions for many users at once (e.g. a group that can create/update/delete an Auto Scaling group). IAM Roles — assumed by anyone/anything that needs them, including letting one AWS service access another (e.g. Amazon EKS assuming a role to manage EC2 for autoscaling — since policies can't attach to EKS directly). IAM Policies — JSON documents defining permissions; validated on every request; an identity can have multiple policies attached.

AWS Shared Responsibility Model in Security

AWS secures the cloud; the customer secures what they put in the cloud.

The split AWS responsibility — "Security OF the Cloud": the hardware, software, networking, and facilities running AWS Cloud services. Customer responsibility — "Security IN the Cloud": varies by which services you use — this determines how much configuration work falls on you.
How responsibility shifts by service type

Amazon EC2 (IaaS)

You control the entire solution — OS, patches, application software, and the security-group firewall configuration. Full customer responsibility for guest-OS-and-above.

Amazon RDS

A "containerized" middle ground — you configure it and control access, but AWS handles the internals of how the engine functions.

Amazon S3 / DynamoDB (abstracted)

AWS operates the infrastructure, OS, and platform. You're responsible for the data itself — encryption options, classification, and IAM permissions.

Key components of the shared model

Infrastructure Security

AWS: data centers, hardware, network. Customer: instances, databases, other resources.

Network Security

AWS: secure network infra. Customer: security groups, NACLs, VPC settings.

Data Protection

AWS: encryption/backup tooling. Customer: implementing encryption, access controls, backups.

IAM

AWS Key Management Service (KMS)

A managed service to create, control, and manage the cryptographic keys that encrypt and protect your data — backed by hardware security modules (HSMs).

Symmetric vs. asymmetric Symmetric key — the default, most-used type; same key encrypts and decrypts; never leaves KMS unencrypted. Asymmetric key — a mathematically related public/private pair; the private key never leaves KMS unencrypted (must call KMS to use it), while the public key can be used via KMS API calls.
Client-side vs. server-side encryption

In client-side encryption you encrypt data and manage your own keys (optionally using KMS). In server-side encryption, AWS (e.g. via EBS or S3) encrypts your data and manages the key for you, using KMS underneath — the common option for most AWS services.

Envelope encryption — how it works

Encryption

1. Data is encrypted with a Data Key → Encrypted Data.
2. The Data Key is itself encrypted with the Master Key → Encrypted Data Key.
3. Encrypted Data Key is stored alongside the Encrypted Data.
4. The plaintext Data Key is deleted.

Decryption

1. Ask the Master Key to decrypt the Encrypted Data Key → recovers the plaintext Data Key.
2. That Data Key is used to decrypt the actual Data.

Types of KMS keys

Customer Managed Key

Created and controlled by your organization.

AWS Managed Key

Created by AWS services that use KMS to encrypt your service resources.

AWS Owned Key

KMS keys created and used by AWS services within an AWS service account.

Key concepts

Key Policies

JSON policies defining who can use/manage a key.

Key Aliases

Friendly names for easier key management.

Grants

Temporary, granular permission to use a key.

Encryption Context

Key-value pairs cryptographically bound to the ciphertext for integrity.

Key Rotation

Automatic or manual regeneration of key material over time.

Key Import

Bring your own key material into KMS and control its lifecycle.

Multi-Region Keys

Replicate a key across Regions for availability/DR.

CloudTrail Logging

Every KMS operation is logged for audit and tracking.

Use cases

Securely managing blockchain (Ethereum) account credentials via a customer master key · encrypting PII in S3 with SSE-KMS · encrypting RDS databases and their backups · encrypting application secrets alongside AWS Secrets Manager · multi-Region key replication for disaster recovery with centralized key policy.

1

Scalability

Horizontal: add more resources (e.g. more EC2 instances). Vertical: upgrade an existing resource's specs.

2

Scalability and Elasticity in Cloud Computing

Related but distinct: one handles sudden short-term spikes, the other handles sustained long-term growth.

Cloud Elasticity

Automatically expands/compresses infrastructure to match a sudden, temporary spike or drop in demand — minimizing infrastructural cost. Not suited to workloads needing persistent capacity. Example: an online store scaling up for a Christmas traffic spike, then scaling back down once the season ends.

Cloud Scalability

Handles a growing workload where good performance must be sustained — used where persistent resource deployment is required. Example: a company's database growing steadily as the business grows, so capacity is scaled up to match.

Vertical (Scale-up)

Increase the power of an existing resource.

From the notes: definitions, services, best practices

Scalability = handle increasing load by adding resources while maintaining performance. Elasticity = automatically increase or decrease resources as demand changes (automatic adjustment · cost-efficiency · rapid scaling). 5.4

High Availability and Fault Tolerance

Both remove single points of failure through redundancy — but they guarantee different things.

High Availability A system maintains uptime almost always, though sometimes in a degraded state. AWS's benchmark is 99.999% ("five nines") — roughly 5 minutes 15 seconds of downtime per year. Achieved by removing single points of failure via redundancy (e.g. a backup server if the primary server room floods).
Worked example — mobile banking app

Servers span multiple Availability Zones, each holding identically configured EC2 instances. If one AZ fails, the app points to instances in the backup AZ — no single point of failure.

The primary database is replicated to a read-only database in a separate AZ. If the primary AZ goes down, users can still view balances (reads) but can't transfer or withdraw funds (writes) — HA guarantees essential services, not full functionality, and the backup may lag (e.g. replicating once a day).

Fault Tolerance — "HA's older brother" A system maintains uptime with zero user-visible disruption during a primary outage — historically far more expensive than HA, requiring load-balanced servers, replicated databases, and multi-Region availability, all self-managed pre-AWS.
Worked example — e-commerce app (fault tolerant + highly available)

Compute: microservices in Docker containers on Amazon ECS with Fargate (no infrastructure management).

Data: Amazon Aurora Global Database replicates across Regions — the app keeps running from another Region during a regional outage.

Resilience: AWS Lambda + API Gateway give a serverless, auto-scaling layer that avoids single points of failure.

Testing & monitoring: AWS Fault Injection Simulator (FIS) simulates failures (network latency, instance termination) to find weaknesses; CloudWatch Container Insights gives detailed container metrics/logs; Amazon Q can be queried for resilience-improvement suggestions.

From the notes: characteristics, services, how to achieve

HA characteristics

Achieved via redundancy and failover: multiple instances across AZs/Regions · automated failover to healthy resources · continuous health checks.

FT characteristics

No single point of failure · graceful degradation (no total loss of functionality) · self-healing (detect and recover automatically).

Services for HA

EC2 + ELB across AZs · RDS Multi-AZ (standby in another AZ) · S3 (data across AZs) · Route 53 (DNS failover) · Auto Scaling.

Services for FT

EC2 Auto Scaling (replaces unhealthy instances) · S3 and EFS (replicated across AZs) · ELB (stops routing to failed instances) · DynamoDB · Lambda · CloudFront (multiple edge locations).

How to achieve both: multi-AZ and multi-Region deployments · load balancing + Auto Scaling · data replication and backup (RDS Multi-AZ, DynamoDB Global Tables, automated backups, AWS Backup) · self-healing architectures (CloudWatch alarms trigger recovery; Lambda or Step Functions automate it). Benefits: improved reliability, business continuity, better user experience, automatic recovery. Challenges: complexity, cost, data consistency across AZs/Regions, latency of multi-Region.

DynamoDB

Monitor Consumed Read/Write Capacity Units in CloudWatch, then use Auto Scaling (scale in/out automatically) or the on-demand pricing option to pay only per request.

EBS Volumes

Trusted Advisor's Underutilized EBS Volumes check flags volumes with <1 IOPS/day over 7 days → snapshot (via Data Lifecycle Manager), then delete.

Networking

7.1

Amazon Route 53

A highly available and scalable cloud DNS web service — it routes end users to internet applications by translating human-readable names like www.vit.ac.in into numeric IP addresses like 192.0.1.1 that computers use to connect.

How internet traffic is routed — the 9 steps
A user opens a browser, types www.example.com and presses Enter. The request is routed to a DNS resolver, usually managed by the ISP — a cable provider, DSL broadband provider or corporate network.
The ISP DNS resolver forwards the request to a DNS root name server.
The resolver forwards again, this time to a TLD name server for .com domains. The .com name server responds with the names of the four Route 53 name servers associated with example.com. The resolver caches those four name servers — next time someone accesses the domain, steps 3 and 4 are skipped. Name servers are normally cached for two days.
The resolver chooses one Route 53 name server and forwards the request. That name server looks for the www.example.com record in the hosted zone example.com, gets the associated value — e.g. the web server IP 192.0.2.44 — and returns it to the resolver.
The resolver returns the IP to the browser. The browser sends a request to that IP — where your content lives, e.g. a web server on an EC2 instance or an S3 bucket configured as a website endpoint. The web server returns the page and the browser displays it.
What Route 53 does

Domain registration & management

Register a new domain or transfer an existing one. Once registered, configure DNS settings freely — mail server setups (MX records), domain aliases and more.

Global DNS resolution

A worldwide anycast network of DNS servers placed strategically around the globe returns the IP matching the domain — low latency, high performance, accessible from anywhere.

Traffic routing & load balancing

Distribute incoming traffic across multiple endpoints — EC2 instances, Elastic Load Balancers or external resources — using DNS-based latency routing, weighted round-robin and failover setups.

Functions of Route 53
  • If a web application requires a domain name, Route 53 registers the name for the website.
  • When a user enters the domain name, Route 53 connects the user to the website.
  • If a failure is detected at any level, it automatically routes the user to a healthy resource.
  • It is cost effective, secure and scalable.
  • It is flexible, highly available and reliable.

Objects in a hosted zone that determine how internet traffic is routed for a domain so it reaches the resources. Each record's name must end with the name of the hosted zone.

A request for information sent from a DNS client to a DNS server.

Servers in the DNS that translate the domain name into an IP address so traffic can be routed to the resources.

Determines how Route 53 responds to queries.

Also DNS failover, health checks (HTTP/HTTPS/TCP), DNSSEC, Traffic Flow (visual routing configs), anycast DNS, CloudWatch integration; routes to EC2, S3, ELB, CloudFront, Lambda. Challenges: cost with many queries/health checks, complex advanced policies, domain extension limits, AWS dependency, complex failover setup.

7.2

Amazon CloudFront

A globally distributed network of servers that delivers content to users — a CDN with edge servers in many locations that cache content closer to users to improve access speed.

Caching data in multiple locations also gives data redundancy, improving reliability of access. CloudFront uses RTMP (Real Time Messaging Protocol) for video streaming and HTTP/HTTPS for web content. CDNs suit bulky data — video streaming, large file and software downloads — and make website access faster. Creation of new distributions can be automated.

Cache hit vs cache miss Cache hit — the requested content is already at the edge data centre, so it's served immediately. Cache miss — CloudFront requests the content from the origin (web server or S3); the request flows through the AWS backbone, is delivered to the customer, and a copy is kept for future requests.
Security bonus Using CloudFront adds a layer of security because your origin server is not directly exposed to the public network — and it integrates with AWS WAF (Web Application Firewall).

Web Application Firewall (WAF)

A Web Application Firewall protects a web application by filtering, monitoring and blocking malicious HTTP/S traffic that might penetrate it. In simple terms, it acts as a shield between a web application and the internet, protecting it from different types of attacks.

From the notes: features and challenges

Global CDN with 400+ edge locations caching static and dynamic content with low latency. Features: custom caching rules (headers, query parameters, cookies) · SSL/TLS and HTTPS · AWS Shield Standard · WAF integration · field-level encryption · Lambda@Edge (A/B testing, personalization, header injection) · origins (S3, EC2, external HTTP) · streaming (HLS, DASH, live) · geo-restriction · signed URLs and cookies · CloudWatch metrics (cache hit/miss, latency, errors) and access logs to S3 · pay-as-you-go with a free tier (1 TB transfer and 2 million requests per month). Cache lifetime set by TTL; invalidation manual or automatic. Challenges: cache invalidation, cost at high volume, uneven geographic coverage, not for every real-time need.

7.3

Amazon API Gateway

An AWS service for creating, publishing, maintaining, monitoring and securing REST, HTTP and WebSocket APIs at any scale.

API developers can create APIs that access AWS or other web services, as well as data stored in the AWS Cloud — for their own client applications, or made available to third-party app developers. The RESTful APIs it creates are HTTP-based, enable stateless client-server communication, and implement standard HTTP methods: GET, POST, PUT, PATCH, DELETE.

The "front door" metaphor API Gateway acts as a front door for applications to access data, business logic or functionality from backend services — workloads on EC2, code on Lambda, any web application, or real-time communication applications. It handles all the tasks involved in accepting and processing up to hundreds of thousands of concurrent API calls: traffic management, authorization and access control, monitoring, and API version management.
Features

Stateful and stateless APIs

WebSocket (stateful) plus HTTP and REST (stateless).

Flexible authentication

IAM policies, Lambda authorizer functions, and Amazon Cognito user pools.

Canary release deployments

Roll out changes safely to a fraction of traffic first.

Logging & monitoring

CloudTrail logging of API usage and API changes; CloudWatch access logging and execution logging, with alarms.

Custom domain names

Serve APIs under your own domain.

AWS WAF integration

Protects APIs against common web exploits.

AWS X-Ray integration

Understand and triage performance latencies.

CloudFormation support

Templates can enable API creation as code.

The three basic parts
1

Request flow

Everything before the HTTP request hits the backing integration — validating and preparing the request.

2

Integration

Outside API Gateway itself. Where the request is routed once it passes authorization and validation — a Lambda function processing a payload, an HTTP endpoint the request is forwarded to, or another AWS service called directly.

3

Response flow

Everything after the request hits your integration — preparing the response for the client.

Lifecycle step 1 · Authorization and usage plans

Authorization is completely optional, but using it protects downstream resources from excess load. A request can be authorized using Cognito User Pools, AWS IAM, or a Lambda custom authorizer.

API Gateway can be configured to provision API keys that must be passed with any request — used for rate limiting and throttling users. API keys are associated with a usage plan, which configures two things:

Throttling limits

How many requests per second are allowed for a usage plan — prevents a caller from overwhelming downstream resources.

Quota limits

A maximum number of requests over a time period — a day, week or month — enforcing limits on a particular client.

Lifecycle step 2 · Validation with Method Requests

The method request step is primarily for validation of the incoming request, in two parts:

  • Validate parameters — query strings and HTTP headers — by specifying the name of the header or query string.
  • Validate the request payload (request body) by providing a request model (a JSON schema object) to validate against.

To validate either, you must create a Request Validator resource.

Lifecycle step 3 · Transforming with the Integration Request

The integration request step transforms data into the proper shape for your backend. The request object is transformed by writing mapping templates in the Velocity Template Language (VTL), configured per Content-Type.

Integration passthrough When a method request carries a payload and either the Content-Type header matches no specified mapping template, or no mapping template is defined, you can choose to pass the client-supplied payload through to the backend without transformation. That process is called integration passthrough.

In summary: API Gateway is a fully managed service making it easy to create, publish, maintain, monitor and secure APIs at any scale. Use it for building serverless applications, for integrating with legacy applications, or for proxying HTTP requests directly to other AWS services.

From the notes: features and challenges

Fully managed service to create, deploy and manage REST, WebSocket and HTTP APIs; entry point to Lambda, EC2 or any HTTP endpoint; public and private APIs. Features: CloudWatch monitoring · security via IAM, Lambda authorizers, Cognito (also API keys) · rate limiting and throttling · request/response transformation (mapping templates) · versioning · CORS · custom domain names · multiple stages (dev, prod) · response caching · backends: Lambda, HTTP, AWS services, Mock. Flow: create API → define resources + methods → integrate backend → secure → deploy to a stage → throttle/monitor → auto-scales. Challenges: complex pricing, Lambda cold starts, mainly HTTP/HTTPS, fine-grained rate limits need configuration, latency with large payloads, stateful WebSocket management.

7.5

AWS Virtual Private Network (VPN)

A networking service that establishes a secure connection between AWS, on-premises networks and remote client devices. Two variants: Site-to-Site VPN and Client VPN.

Each service provides a managed, scalable and highly available cloud VPN solution to secure network traffic. Site-to-Site VPN establishes a secure tunnel between on-premises and AWS Virtual Private Gateways or Transit Gateways.

Two gateway terms

Virtual Private Gateway (VGW)

The VPN concentrator on the AWS side of the VPN connection.

Customer Gateway (CGW)

A hardware or software device installed on the VPN client side.

AWS Client VPN

A fully managed remote access VPN solution that lets remote employees securely access AWS resources and your on-premises network. It is entirely elastic, automatically adjusting up or down based on demand, so users access applications the same way before, during and after a migration to AWS.

Quickly scale remote access

When circumstances force staff to work remotely, performance and availability can suffer as VPN connections and traffic grow — Client VPN scales to absorb that.

Access applications during migration

Users securely reach applications both on-premises and in AWS — useful while migrating apps to the cloud.

Integrate with authentication and MDM

Supports Microsoft Active Directory authentication via AWS Directory Services, certificate-based authentication, and federated authentication using SAML 2.0 with the AWS-provided OpenVPN client.

Securely connect IoT devices

Certificate-based authentication establishes secure connections between IoT devices and VPC services.

AWS Site-to-Site VPN

A fully managed service establishing a secure connection between your data centre or branch office and your AWS resources using IPSec tunnels. It connects to both Amazon VPCs and the AWS Transit Gateway, and each connection uses two tunnels to boost redundancy.

Accelerated Site-to-Site VPN For globally distributed applications, this option integrates with AWS Global Accelerator to dynamically route traffic to the fastest AWS network path — greater performance than a standard Site-to-Site VPN.

7.6

AWS Transit Gateway

A networking service that connects thousands of Amazon VPCs and on-premises networks using a single gateway — a hub-and-spoke model that routes all traffic to and from each VPC or VPN and provides one place to manage and monitor it all.

In simpler terms, Transit Gateway is a central hub connecting your VPCs and on-premises networks. It simplifies your network and eliminates complicated peering relationships, functioning as a cloud router where new connections are established only once.

Regional scope and redundancy Transit Gateway is a Regional resource and can connect thousands of VPCs within the same Region. You can connect multiple gateways over a single Direct Connect connection for hybrid connectivity. Typically one Transit Gateway per Region is enough, using its routing tables to isolate VPCs where needed. You do not need additional gateways for high availability — they are highly available by design; for redundancy use a single gateway in each Region. Multiple gateways are still valid to limit misconfiguration blast radius, segregate control plane operations, and ease administration.
The two analogies from the deck

Central station

Just as a central station lets you travel anywhere in a city, Transit Gateway connects every part of your network. Instead of separate connections between each pair of networks, everything connects to the hub, and data moving between networks passes through it.

Telephone exchange → mobile network

Traditional architectures are like an old telephone exchange — a physical wire per pair of phones, which gets complex fast. Transit Gateway is like a mobile network: every phone talks to one central network instead of managing a multitude of individual connections.

Benefits — the growing-company example

Imagine you're the IT manager of a growing tech company where every department (Development, Sales, HR) needs its own VPC, and more VPCs are coming, possibly across different geographic regions.

Simplified network management

Without Transit Gateway you'd make individual connections between every VPC — a massive spider web. With it you create one central hub, turning that web into a neat bicycle wheel: gateway as hub, VPCs as spokes.

Enhanced security

With all VPCs connected through one gateway you monitor and control traffic in one place instead of hopping between connections — like a security guard at a building entrance.

Cost optimization

AWS charges for data moving between VPCs. With Transit Gateway, data travelling between VPCs in the same Region usually stays within the gateway, lowering costs — like internal mail instead of postage per document.

Improved scalability

Handles thousands of connections, making it simple to add more VPCs as the company expands — like an open-plan office you can rearrange rather than building new rooms.

From the notes: features and challenges

Fully managed central hub connecting many VPCs, on-premises networks and remote offices (hub-and-spoke). Features: inter-VPC connectivity without peering · on-premises via Direct Connect or VPN · customizable route tables (also network segmentation) · multicast · PrivateLink integration · elastic scaling (thousands of VPCs) · security with AWS Network Firewall and encryption in transit · shared services VPC (DNS, NTP, Active Directory). VPCs connect through VPC attachments. Challenges: cost per attachment and data processing, routing-table complexity, limited Direct Connect gateways per Region, advanced inspection needs extra services, added hop latency, single point of failure without redundancy.

Architecture scenario drills

The design questions from the Module 6–7 decks, with the answer shape each one is looking for. These are the highest-value revision items — the pattern repeats.

1 · Company ABC — disaster recovery for an e-commerce platform

Requirements: geographic redundancy (replicate infrastructure across Regions), traffic routing (direct users to the nearest available Region), automated failover (seamless redirection during outages).

Answer: set up AWS infrastructure in multiple Regions · configure Route 53 geolocation routing · implement Route 53 failover routing for automated redirection.

2 · Company XYZ — fast, secure global delivery for an EC2-hosted site

Requirements: global reach, low latency, secure distribution (HTTPS), scalability under variable traffic.

Answer: configure a CloudFront distribution · set up Route 53 geolocation routing to CloudFront · enable SSL/TLS encryption · use Route 53 traffic flow for scalable traffic management.

3 · Company DEF — streaming media and online gaming, ultra-low latency

Requirements: low latency, high throughput for high-bitrate streaming, global reach, cost optimization, dedicated capacity.

Answer: configure a CloudFront streaming distribution · set up Route 53 latency-based routing · enable CloudFront content optimization · monitor performance with CloudWatch · establish Direct Connect for dedicated capacity.

4 · VideoStream — global video delivery from S3

Requirements: cache videos at edge locations, secure content with HTTPS, support HTTP/2, real-time monitoring and logging, integration with S3.

Answer: a CloudFront distribution with the S3 bucket as origin, HTTPS-only viewer protocol policy, HTTP/2 enabled, and real-time logs to CloudWatch.

5 · VideoStream — geographic access restriction

Requirements: block access from specific countries; allow access from specific IP addresses.

Answer: use CloudFront's Geographic Restriction feature to block specific countries · use IP address restriction to allow specific IPs.

6 · LearnOnline — frequently updating dynamic content

Requirements: cache dynamic content for 1 minute; update the cache every 30 seconds.

Answer: use CloudFront Cache Behavior settings to cache dynamic content for 1 minute · use the Minimum TTL setting to update every 30 seconds · use Lambda@Edge to update the cache dynamically.

7 · SoftCo — tracking software downloads

Requirements: log downloads to CloudWatch and monitor usage metrics.

Answer: enable CloudFront logging to CloudWatch · use CloudFront metrics and analytics to monitor usage · integrate CloudTrail for additional logging and auditing.

8 · GameOn — serving content from multiple origins

Requirements: serve content from S3 and custom origins, using CloudFront routing features.

Answer: use CloudFront's Multiple Origins feature · use routing features to route requests to specific origins · use Cache Behaviour settings to optimize caching.

9 · Sports broadcaster — global live event streaming

Requirements: live streaming server as origin, global edge locations, cache live streams at the edge, HTTPS and DRM security, real-time logging to CloudWatch.

Answer: a CloudFront distribution fronting the live streaming origin, global price class, HTTPS-only with DRM, and real-time logs delivered to CloudWatch.

10 · DynamoDB-backed API surviving a total regional failure

Requirements: stay online during a full Region outage; a couple of minutes of lag or slowness during the failure event is tolerable, with normal operation restored afterwards.

Answer: a multi-Region active architecture — DynamoDB global tables replicating across Regions, API Gateway + Lambda deployed in each Region, and Route 53 failover (or latency) routing with health checks to shift traffic to the surviving Region.

11 · Generic web application on AWS

Requirements: high availability, scalability, load balancing, database integration, HTTPS security.

Answer: EC2 instances in an Auto Scaling group across multiple AZs behind an Elastic Load Balancer, a Multi-AZ RDS database, ACM certificate on the load balancer for HTTPS, and Route 53 pointing at the ELB.

12 · 3-tier weather site — fault tolerance within a 2-AZ Region

Requirements: minimum 6 web tier servers and 6 application tier servers, one RDS database, fault tolerant within the Region.

Answer (the exact deck answer): a web tier across 2 AZs with 6 EC2 instances in each AZ in an Auto Scaling group behind an ELB · an application tier across 2 AZs with 6 EC2 instances in each AZ in an Auto Scaling group behind an ELB · a Multi-AZ RDS deployment.

Why 6 in each AZ, not 3? Fault tolerance means the workload survives losing an entire AZ. If you split 6 servers as 3+3, losing one AZ leaves you with 3 — below the stated minimum. Putting the full 6 in each AZ means the surviving AZ alone still meets the requirement.
13 · XYZ Corporation — global branch offices needing encrypted connectivity

Requirements: secure access to AWS resources for remote employees · site-to-site connectivity between branch offices and AWS · compliance with regulatory requirements for data encryption · authentication and authorization for remote employees.

Answer: AWS Site-to-Site VPN (IPSec, two tunnels per connection) from each branch's Customer Gateway to a Transit Gateway, plus AWS Client VPN for remote employees with SAML 2.0 federated or Active Directory authentication.

14 · ABC Inc. — on-premises data centre to AWS VPC

Requirements: a secure, encrypted connection between the two environments.

Answer: Site-to-Site VPN with a Customer Gateway on-premises and a Virtual Private Gateway attached to the VPC; for multiple branch offices, terminate them all on a Transit Gateway instead.

15 · ABC Corporation — financial services, New York to us-east-1

Requirements: dedicated network connection · latency under 5 ms · 10 Gbps bandwidth · encrypted data transfer · redundancy for high availability.

Answer: AWS Direct Connect at a 10 Gbps port speed via physical cross-connect, with a second Direct Connect at a different location for redundancy, and a Site-to-Site VPN over the internet as a backup path. Because Direct Connect is private but not encrypted by default, run an IPSec VPN over the Direct Connect to satisfy the encryption requirement.
